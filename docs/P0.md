## Implemented P0 behavior

The worker sends `truncate:false` and `shift:false`, decodes `done_reason`, and records a private `generation-<attempt-id>.json` observation after model verification and before finish validation for a newly generated result. It includes the ownership identity, configuration hash, done/reason, bounded output and runtime metrics. Files use the existing atomic private-write path.

Only done=true with reason exactly `stop` qualifies for new completion. Length-limited, unfinished, missing, empty and unknown reasons are terminal generation errors under the current strict policy; they are not blindly retried. Partial output and reason remain in the private observation; they never become an accepted queue output. Failure messages do not echo dataset contents. A natural stop alone is not an input-integrity or semantic validator.

Observation persistence failure prevents the new completion from being sent. Observations contain dataset output, remain outside Git, and are not automatically deleted; retention/quotas belong to operability work. They are local worker artifacts, not a new coordinator database column or export field. Existing accepted results and legacy completion spools are not retroactively revalidated by this change. Use fresh state and rebuilt workers for a future P1 experiment. The trusted-worker completion protocol still trusts worker-supplied output; it is not execution attestation.

## Measurement contract and scope boundary

Initial timings come from one harness's monotonic clock. Queue wait begins at acknowledged/observed committed submission and ends at claim acknowledgment; a harness boundary is an externally observed bound, not an invented internal commit timestamp. Inference timing, runtime-provided durations, completion acknowledgment, failure reconciliation and reassignment are distinct fields. Cross-process/host monotonic timestamps are not subtracted. Reassignment begins at acknowledged fault injection; outage recovery begins only when connectivity/runtime health is restored. Reports must disclose retries, blocking, failed inputs and denominators.

Structured-output acceptance for a future pilot requires an explicit schema, exact ID/cardinality checks and task-specific validators. Runtime format=json support was probed but is not implemented as a BatchDock manifest feature in P0. Missing/invalid JSON or wrong field types cannot count as valid pilot output. General JSON-schema support and product-level validation remain P2 work.

P0 covers baseline reproduction, runtime contract observations, mandatory finish handling and the independently checked short fixture. P1 remains unstarted and requires explicit authorization. Second-Mac access is confirmed in principle; its hardware, installed model/runtime and restricted transport remain unverified. Do not provision it as part of P0. Sleep/restart takeover, failure-delivery durability, infrastructure retry accounting, worker supervision and claim optimization remain P2 gaps.
